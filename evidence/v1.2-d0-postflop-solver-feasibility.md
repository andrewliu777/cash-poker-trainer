# D0.2 Postflop solver feasibility gate — 2026-09-30

## Corrected objective and decision

The user wants postflop decision assessment in this trainer. The earlier D0 preflop data survey answered the roadmap's old wording but did not answer that goal. **Postflop is now the primary D1/D2 track; a push/fold chart is not the feature to ship.** The preflop survey remains an input-source audit only.

**Conditional Go for a first, post-hand, heads-up postflop solver path.** There is a permissively licensed solver implementation capable of reporting per-combo action EVs and measured exploitability. The first integration target is a heads-up **river** decision with explicitly supplied, versioned ranges and an exact matching action tree. Turn and then flop follow after resource and line-mapping checks. This is a real solve of a stated two-player game, not a universal score of the original hand. Multiway postflop solvers exist, but the selected open engine is heads-up only. **No-Go for automatic GTO grades on every 2–6-seat hand** until starting ranges, multiway integration, arbitrary bet sizes, browser execution, and convergence are addressed.

**Decision:** Keep D1's hero-visible snapshots valid for every player count. D2's first executable path remains the licensed MIT heads-up river engine. Add a separate multiway feasibility gate before promising three-player or four-to-six-player EV grades: obtain an authorized integration path, verify range and betting-tree inputs, run a matching hand through the solver, and inspect per-action EV plus solve quality. A multiway product's existence alone does not authorize automatic use in this app.

The follow-up [D0.4 six-way survey](./v1.2-d0.4-six-way-postflop-solver-survey.md) checks the stricter case of six players **still active after the flop**, including IkaSolver, MonkerSolver, open research code, and misleading six-seat/head-up product labels.

## What the hand history can and cannot feed to a solver

For a completed hand, `js/shared/handHistory.js` gives the hero-visible prefix before each human `action.applied` event: hole cards, board, folded seats, public action order and amounts, pot, stacks, street bets, and rake=0. `js/shared/handReview.js` already anchors replay at an event sequence. The postflop adapter must start from `projectSeatHandHistory`, never from an internal omniscient bot record. Revealed opponent cards later in the hand are **future information** for an earlier decision and cannot be a default range input.

At the first heads-up flop decision, the event prefix can supply board, pot, OOP/IP order, remaining stacks, and subsequent action line. A solver additionally needs **both starting ranges** and a fixed bet-size tree; neither is in the hand record. At a turn or river decision, a flop-root solve can carry range reach through earlier actions/runouts. Solving only from a later street without such reach requires the user to explicitly supply later-street ranges, and the result must be labeled conditional on those inputs.

The history supports arbitrary legal chip-size raises. A solver tree has only its configured sizes. If a recorded bet/raise is absent from that tree, the adapter must return `unavailable` for numerical EV loss; silently snapping 37% pot to 33% or 50% changes the game. Two active players with side pots or unequal all-in eligibility also need a separate rules match; initially exclude them. A 6-seat table that reaches a heads-up flop still needs valid ranges conditioned on its **multiway preflop** path, so it does not automatically qualify as a 2-seat HU solution.

## Browser and packaging facts

The preferred engine's inspected `wasm/src/lib.rs` exposes a browser integration pattern: run `solve_spot` inside a Worker, call `tree_stats` first, send progress, and open the result handle to query node action/EV arrays. Its browser worker imports generated WASM glue and fetches the binary by URL. The current trainer has a strict `script-src 'self'` CSP in `index.html` and is being viewed via `file://` in the app. [MDN documents](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Guide/Modules) local module/fetch restrictions and [WASM CSP requirements](https://developer.mozilla.org/en-US/docs/WebAssembly/Reference/JavaScript_interface/instantiateStreaming_static). D2 must demonstrate the supported launch path (likely local HTTP/HTTPS static hosting), set only the CSP permission needed for WASM, and keep solving after the hand rather than during action. The source's single-threaded browser build avoids a COOP/COEP multithreading requirement but may be slow.

This trainer's `agents.md` currently forbids new runtime dependencies and build steps. A real solver cannot be described as dependency-free. The candidate could be developed as a separately built, pinned, MIT-attributed WASM artifact consumed by plain JS, with no npm/toolchain required for *players*. That exception and its source/binary provenance must be explicit at implementation time; no binary or dependency was added by D0.

## Revised D1/D2 acceptance sequence

1. **D1: postflop spot extraction.** Identify every human flop/turn/river decision in completed hands and build a hero-visible decision snapshot. Include board, pot, remaining stacks, OOP/IP, exact public action line, hero combo, and missing-input reasons. Reject future-card leakage. This can be tested with existing JS and hand-history fixtures, independent of solver runtime.
2. **D2a: real HU river solve.** Build the pinned MIT engine outside the app, verify its test/fixture output and WASM asset hash, then solve one actual completed HU river spot from this trainer using explicit two-player ranges and an exact action tree. Show each available action's EV for the hero combo, selected action, EV difference, range provenance, bet-tree version, and measured exploitability. If the selected action has no matching child, the hero combo is blocked, or the opponent's compatible range mass is zero, show unavailable; a hero action's zero equilibrium frequency alone does not make its deviation EV undefined. An EV difference is relative to **the chosen model**, not a judgment against the bot's unrevealed actual cards.
3. **D2b: turn, then flop.** Carry ranges/reach from the earliest solved street, preserve the observed betting line and board runout, and enforce a memory/time preflight. Solve only a tree that fits the budget and includes the real action sizes; otherwise explain why unavailable. Full-flop solves and bulk analysis of every hand are not presumed feasible in a normal browser tab.
4. **Range quality gate.** Start with explicit user-provided ranges or clearly labeled presets solely for study. Automatic ratings of ordinary hands require a validated range source for the preflop formation and subsequent line. Neither random ranges nor bot hole cards may be silently treated as GTO ranges. Multiway postflop remains unavailable **in the selected HU integration path**, pending the separate multiway gate above.

- Inspected local hand-history replay and CSP. No automatic range reconstruction or exact solver-line mapping exists yet. D1 must produce these inputs/rejection reasons before UI scoring.
- No gameplay or analysis UI was changed in D0. The next implementation milestone is the postflop snapshot/adapter, not a push/fold trainer.
